# KatzLab ureteroscope — Python control

Gamepad control of the three motion axes and the Dornier laser, with all logic
in Python and the Teensy reduced to executing commands.

## What this replaces

The rig previously ran as separate Arduino sketches, each driven by typing into
the Serial Monitor, with the gamepad read by the Teensy itself. Everything is
now driven from here.

| Original sketch | Status |
|---|---|
| `3DOF_MovementF.ino` | wrapped — its text protocol is spoken by `drivers/motion.py` |
| `shootingyesready_inoF-1.ino` | wrapped — its command set is spoken by `drivers/laser.py` |
| `Teensy_Linear_OpenLoop_Controller_Homing.ino` | superseded — the control loop lives in Python now |
| `Teensy_Linear_OpenLoop_Serial_Homing.ino` | superseded |
| `Standalone_Controller_Diagnostics.ino` | superseded by `scripts/calibrate_controller.py` |

## Setup

```bash
cd python
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
```

Flash the merged firmware once (see [Firmware](#firmware) below), then:

```bash
./.venv/bin/python scripts/calibrate_controller.py
```

This walks through each stick and button once and writes `config/controller.yaml`.
It has to be done per controller — axis and button indices differ between
models, and analogue triggers appear as buttons on some and as axes on others.
The readout updates live, so you can see each control register as you move it.

If anything looks wrong, the live monitor shows every axis and button at once:

```bash
./.venv/bin/python scripts/gamepad_monitor.py
```

That is the replacement for `Standalone_Controller_Diagnostics.ino`. Use it to
read indices off by hand and write them straight into `config/controller.yaml`
if the wizard is being awkward.

## Running

```bash
./.venv/bin/python -m katzlab ports        # which serial port is the Teensy
./.venv/bin/python -m katzlab selftest     # check everything; moves nothing
./.venv/bin/python -m katzlab run          # the control loop
./.venv/bin/python -m katzlab run --no-laser
./.venv/bin/python -m katzlab monitor      # passive serial monitor
```

## Control map

| Input | Action |
|---|---|
| Left stick | linear travel |
| Right stick up/down | rotation |
| Right stick left/right | flexion |
| Left secondary (bumper) | Enable + Ready |
| Left primary (trigger) | Standby |
| Right secondary (bumper) | Fire |
| Right primary (trigger) | Pause |
| X (bottom of right cluster) | **Emergency stop** |
| H (right of right cluster) | Home all axes |

All three sticks are rate controls: deflection sets a speed. Flexion holds its
angle when the stick is released rather than springing back to zero — the stick
moves the absolute tip target, it does not command a position directly.

After an e-stop, press **Standby** to acknowledge. The laser stays disarmed
until Enable/Ready is pressed again.

## Configuration

`config/system.yaml` holds every limit and calibration constant, mirroring the
firmware's own. Python pre-clamps against these so the firmware never has to
reject a command; the firmware limits remain the authoritative backstop.

`config/controller.yaml` is generated by the calibration script. If an axis
moves the wrong way in use, flip its `invert` flag rather than re-calibrating.

### Where the controller is plugged in

`input.source` selects the backend, so this is a one-line change:

- `mac_gamepad` — controller on the MacBook, read via pygame. **Current setup.**
- `teensy_host` — controller on the Teensy's USB host port, state streamed up
  the serial link. The Python side is written; the firmware bridge that
  publishes `GP` telemetry frames is not, so this is not usable yet.

Either way Python owns the mapping and every control decision.

## Firmware

Both original sketches are needed at once on a single Teensy, but each defines
its own `setup()` and `loop()`. Those are the *only* colliding symbols — every
global, constant and helper is distinct, and the command alphabets do not
overlap. So they are merged mechanically:

```bash
./.venv/bin/python scripts/build_merged_firmware.py
```

This writes `../firmware/Combined_Motion_Laser/Combined_Motion_Laser.ino`. The
two original sketches stay the source of truth — edit those and re-run, do not
edit the generated file.

### Building

Verified compiling for Teensy 4.1 with `arduino-cli` and the `SCServo` library:

```bash
arduino-cli compile --fqbn teensy:avr:teensy41 ../firmware/Combined_Motion_Laser
```

| Sketch | FLASH | RAM1 variables |
|---|---|---|
| `3DOF_MovementF` | 70,128 | 41,024 |
| `shootingyesready_inoF-1` | 15,980 | 9,952 |
| **`Combined_Motion_Laser`** | **75,504** | **46,176** |

Under 1% of the Teensy 4.1's flash. All three build clean, so the merge costs
nothing structural.

Flash with the Arduino IDE, Teensy Loader, or `arduino-cli upload`. Remember to
de-energise the relay supply first — see [Safety](#safety).

Dispatch is unambiguous:

| Input | Goes to |
|---|---|
| three numbers | motion: relative mm, relative deg, absolute flexion deg |
| `home` / `h` | motion: home all axes |
| `e r f p s x 1 2 3 4 o g t y w ?` | laser |
| `q` | toggle terse output |

Terse mode suppresses the verbose prompt and per-move status block. A host
issuing ~20 commands a second cannot afford them; at 115200 baud the full
prompt alone is most of the budget. The drivers work either way, but `q` should
be sent once after connecting.

## Known limits of this approach

These are inherent to wrapping the existing sketches, and none of them can be
fixed with more Python:

- **A move cannot be interrupted.** The motion firmware runs each command to
  completion before reading serial again. Chunk sizes are capped in
  `system.yaml` so no single move lasts more than roughly a tenth of a second,
  which bounds e-stop latency to about one chunk — but not to zero.
- **On a single board, a laser stop queues behind an in-flight motion command.**
  Both drivers share one serial port. Same mitigation, same residual latency.
- **Jogging is a stream of small discrete moves,** not continuous velocity, so
  it feels steppier than the old joystick sketch did on the linear axis alone.
- **Top speed is the firmware's,** ~1.5 mm/s linear: the sketch pulses at a
  fixed 800 µs and has no acceleration ramp.

Removing all four needs the firmware rewrite — a thin non-blocking command
server with the control loop in Python.

## Safety

Full laser procedure, arming sequence and troubleshooting: **[LASER.md](LASER.md)**.

### Live fail-safe hazard

`READY_ON_NC` is `true`, so **pin 8 is on the relay's NC terminal.** Comments in
that sketch claim it was moved to NO; they are stale and are not what the build
follows.

NC wiring inverts the ready channel:

| pin 8 | coil | contact | laser |
|---|---|---|---|
| LOW | released | **closed** | **ARMED** |
| HIGH | energised | open | standby |

Standby depends on the coil *staying energised*. A Teensy reset, USB replug,
firmware upload, loose jumper, or loss of the relay supply all release the coil
and **arm the laser with nobody commanding it.** Flashing the merged firmware
does exactly that for the duration of the upload.

**De-energise the relay supply before flashing. Do not leave the rig energised
unattended.**

The real fix is hardware: move the pin 8 wire from NC to NO, set
`READY_ON_NC = false` in `shootingyesready_inoF-1.ino`, and regenerate. Then
de-energised means standby and power loss is fail safe.

What the software already does about it: `setupLaserOutputs()` writes the safe
level *before* `pinMode()`, so pin 8 drives standby the instant it becomes an
output instead of glitching through armed first, and `setup()` runs
`laserSetup()` before `motionSetup()` so that happens as early as possible.
That closes the reset-to-setup window. It cannot close the window while the
board is held in reset or being programmed — the pin is not an output then.
That window is hardware, not firmware.

### Software-side safety

None of this substitutes for the hardware interlock:

- Laser interlock (`e` → `r` → `f`) and dwell timers stay enforced in firmware.
  Python mirrors the state and refuses to send a fire it knows will be rejected.
- The laser is forced to a disarmed state at startup (`safety.start_disarmed`).
- A watchdog trips if controller frames stop arriving — a dropped Bluetooth link
  is treated as an e-stop, not as "hold the last commanded rate".
- Ctrl-C and any unhandled exit relock the laser.

./.venv/bin/python -m pytest tests/ -q

## Troubleshooting

**Reads "Connected" in System Settings > Game Controllers, but Python sees no
controller.** Known and handled automatically. macOS's GameController framework
claims pads it recognises, and SDL prefers that MFi backend — but for many
third-party and clone pads the MFi path exposes nothing at all. The code detects
the empty result and re-initialises with `SDL_JOYSTICK_MFI=0`, forcing SDL onto
the IOKit HID backend. Startup logs say which backend found the device.

Two side effects worth knowing: the controller reports a *different name* on
each backend (this rig's pad is "2In1 USB Joystick" to macOS and "Retro-bit
Controller" to SDL/IOKit), and it can expose a **different axis and button
count** — 4 axes / 13 buttons on IOKit here, where the MFi name suggested 16
axes. Triggers that were axes on one backend may be buttons on the other. This
is why calibration is per-setup, and why the wizard accepts either.

**"It connects but I can't tell if input is going."** Run
`scripts/gamepad_monitor.py`. Every axis and button redraws live, so any press
produces visible movement. If nothing moves there, the controller is not
reporting and the problem is upstream of this code — re-pair it, or try a
wired connection.

**Sticks read 0.000 but triggers read -1.000.** That is normal at rest. Analogue
triggers idle at -1.0 and swing to +1.0 when pulled; sticks idle at 0.

**An axis moves the wrong way.** Flip its `invert` flag in
`config/controller.yaml`. Re-calibrating is not necessary.

**`selftest` fails at the firmware handshake.** The merged sketch is probably
not flashed — one of the original sketches alone will not answer both probes.
Check with `scripts/gamepad_monitor.py`-style raw output via
`python -m katzlab monitor`.
